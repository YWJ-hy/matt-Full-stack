# Matt / Orca 需求拆分、派单与合回修改计划

已在工具包 1.15.0 实施，并同步到 PEIS 的 Matt、Frontend、Backend、Quality 四个 bot。原方案基线为 1.14.0。验证范围见[验证记录](../../VALIDATION.md)。

用户可以把整个需求包交给 Matt，也可以直接找前端或后端排查问题。计划补齐两个入口之间的任务登记、复杂需求的拆分判断，以及多人同时修改代码时的合并与验收。用户在发起工作的会话里看到结果。

## 1. Matt 收到需求包时怎样判断

先读需求包、相关实现和项目约定，用一句话说清用户要得到的结果。规格评审时用一句话说明建议采用哪种方式及原因。

| 判断 | 采用方式 | PEIS 示例 |
|---|---|---|
| 一个业务结果，做法清楚；拆开后不能更早交付、开工或验证关键假设 | 按单项需求派发。公共规格列业务场景，分端规格写各端职责 | 修改预约日期后重新打开仍显示新日期。页面、接口、数据库和异常用例都服务于同一结果 |
| 至少两个可以分别验证的业务结果，且用户可以选批次，或不同任务确实能独立推进 | 按业务结果拆子任务，每项写清能交付什么、由谁实现、如何验收 | 前台改期与主管查询改期记录可以分别交付 |
| 只有一个最终结果，但存在关键技术未知、真实的先后依赖，或失败后返工、回滚代价较高 | 保留一个业务任务和一次整体验收，列出实现阶段。每阶段写明要解决的问题、继续所需的证据以及交给下一阶段的产物 | 团体预约须整批成功或回滚。先验证中途失败时已写入的数据能全部恢复，再接完整名单与页面 |

文档长度、页面数、文件数、同时涉及前后端或测试用例多，都不足以单独触发拆分。判断时还要考虑共享状态是否必须一致、并行工作的协调成本、迁移和兼容性影响，以及依赖究竟阻塞开发还是只阻塞验收。只需确定业务规则时由 Matt 集中向用户澄清；技术未知可用最小实验取证。只有全链路接通才可验证时，先走通最小的真实链路。

单项需求沿用已有规格。需要安排多个子任务或有意义的阶段时，才在 `spec/<需求名>/` 生成 `tasks.md`。同一需求可按业务子任务拆分，并只给其中有风险的任务列阶段。已有工单直接引用，需逐单跟踪时才按父目录约定建单。

## 2. 规格、批准与派单

1. Matt 起草同一修订的 `shared.md` 和涉及端的规格。前后端都依赖的接口方法、路径、字段、成功与失败响应、权限和状态变化写在公共契约里。责任端发现契约缺口时交回 Matt。
2. `tasks.md` 用稳定编号关联交付结果、责任端、场景 ID、开发前置条件、联调验收前置条件、状态及交付记录。阶段注明所属任务。例如查询接口契约确定后前后端可以并行实现；验证“真实改期后查到记录”才需要等待两端及改期功能就绪。
3. 启用 E2E 时，Quality 在开发前从公共规格独立设计用例，关联场景和任务编号。Matt 把用例暴露出的业务歧义、规格和拆分方案放进同一次评审。记录用户批准的修订及全部或部分任务，例如“只做 T01、T03”。若 T03 真正依赖未批准的 T02，说明缺项，等待调整批次。
4. 批准后，Matt 只派本批中开发条件已满足的工作。收到交付或阻塞回执后更新记录，继续派发已解锁的任务。待联调的项目保留验收状态，其他独立工作可以继续。在原会话可查询已完成、进行中、待开始、阻塞原因及证据。
5. 新证据表明原安排不合适时，记录依据并调整执行顺序或实现阶段。涉及业务行为、公共接口或获批范围变化时，暂停受影响部分，提交修订并等用户确认；同一批准范围内的常规派单无需逐单确认。

## 3. 前端或后端 bot 直接接单

| 用户意图 | 接单 bot 的动作 |
|---|---|
| 答疑、只排查 | 读取对应版本，按需要复现和定位，在原会话返回依据。用户要求修复后进入修改流程 |
| 本端缺陷、行为已明确的局部修改 | 明确的“请修复”或修改要求即为本单授权。缺陷先用 `diagnosing-bugs` 复现，再修复、回归并重跑原操作；局部修改按已说明的预期验证，沿用轻量交付记录 |
| 已派需求的返修 | 按需求、任务编号或工单查找原负责人、会话、版本和 worktree。在新聊天里提出也续接原工作，修复后交回新版本复审 |
| 新增业务行为、需改公共接口或另一仓库 | 接单方把现象、已知证据和待决定的问题交给 Matt。Matt 协调规格和批准范围，原接单会话向用户回报进度与结果 |

在实际开工前，Matt 和直收任务的 bot 共用可查询的派单记录，登记需求或修复引用、责任端、当前执行者、返回会话和 worktree。重复来单、同时认领或回执不明时先核对已有记录，再续接或派发，保证同一任务在同一仓库只有一个写入方。简单修复也能被 Matt 查到，无需另建正式工单或多一次审批。用户也可以一直在 Matt 的原需求会话提问，由 Matt 核实后答复。

## 4. 工作树、依赖与团队合并

- **开工。** 启用 worktree 的实现角色按“独立派发任务 × 涉及仓库”建树。一个跨端任务对应两个仓库各自的任务分支；同仓两项独立任务各用一棵树。连续阶段和返修沿用本任务的树。只读审查按角色配置绑定固定提交或核实过的完整补丁。
- **起点。** 记录每端原分支、目标分支、实际起始 SHA、任务分支和目录。独立任务从约定起点创建；若实现依赖另一任务的代码，选取包含该交付的已核实提交，并单独记下最终合回目标。依赖只有未提交修改时标记缺项。由 Orca 原生创建、绑定和执行仓库 `orca.yaml` 的继承初始化策略，核对结果后再开发。
- **试合并。** Matt 按真实依赖安排顺序。各端核对本地目标分支，有共享远端时先 `fetch` 其对应分支，查清两边是否前移或分叉。在隔离工作树验证拟合入的组合，记录任务、目标及试合并的版本。仅在本单明确依赖时纳入同事尚未合入的分支或 PR，保留他人的未提交修改。
- **冲突归属。** 原实现 bot 从双方提交、工单、PR 和获批规格还原改动意图。可兼容的技术差异由责任端整合并测试双方行为。业务预期互斥且规格无法裁决时，Matt 汇总具体分歧、选项和受影响范围，让用户或规则负责人决定。即使 Git 自动合并成功，也要测试组合行为，例如新批量入口是否同样执行同事增加的权限校验。
- **复验与合回。** Quality 对拟交付版本做独立的规范和规格审查，核对本端测试；启用 E2E 时用预定用例验证实际运行的前后端版本对。Matt 列出已验证分支、目标、结果与未验证项，按用户选择合回。落地前再核对版本，目标或任务提交变化就重建组合、重验受影响部分。团队使用 PR 或合并队列时遵循现有规则；推送、发布或关闭远端工单按各自授权执行。
- **清理。** 合回与清理可一次授权，也可分别决定。按任务核实所需验证已完成、改动确已合入、工作树干净、后续任务及测试服务已释放该目录，再用 Orca 清理指定 worktree。只依赖已合入提交的后续任务不妨碍清理。保留任务分支，删分支须有相应授权。待返修、尚有本地改动或下游仍在用时保留现场并说明原因。

## 5. 复用现有能力

| 已确认的能力 | 后续改动如何衔接 |
|---|---|
| 四个 bot 的职责与模型 | Matt 调度，Frontend、Backend 实现，Quality 审查和验收。本次显式模型优先，其次角色显式模型，最后用接单 bot 自身默认。Standards、Spec 的接单方都是 Quality |
| 测试用例与执行工具 | Orca 用例存于需求目录的 `acceptance.md`，Midscene 复用对应 YAML 及具名 case。关闭 E2E 时记录本端验证与“未执行 E2E”。PEIS 当前为关闭、预设 Orca；旧版仅有 `enabled: true` 的项目仍按 Midscene 执行。工具或环境缺项按用例标为未验证 |
| Matt Pocock skills | 借鉴 `to-tickets` 的业务拆分和阻塞关系、`implement-spec` 的依赖调度、`to-spec` 的规格写法。三个原版均是手动入口。现有澄清、领域建模、TDD、故障定位和代码审查各自在相应阶段使用。研究、原型、工单分类按需使用 |
| 冲突处理与项目约定 | 借鉴已归档的冲突指南中“查双方改动依据、验证合并结果”的做法，由现有角色执行。PEIS 父目录已有工单和领域约定，可直接复用；启用工单分类时再补标签映射。[上游合并冲突参考](https://github.com/mattpocock/skills/blob/6f7f7831a625f040a8e06a0e7954826b87ce775a/docs/engineering/resolving-merge-conflicts.md) |

## 6. 实施顺序与验收

| 顺序 | 拟改位置 | 交付与验证 |
|---|---|---|
| 1 | `templates/matt-full-stack/SKILL.md`、`templates/spec/`、`src/release.mjs` | 加入拆分判断、按需使用的任务清单模板和部分批准规则。用“预约改期”“改期及主管查询”“团体改期事务回滚”分别演练三种判断。简单需求的交付目录没有多余清单 |
| 2 | `templates/matt-full-stack/references/dispatch.md`、`issues.md`、`templates/orca/protocol.md` 与各角色说明 | 接通直收任务与 Matt 的认领、回执、状态和解锁规则。验证重复报障能续接、未批准项目不派发、只有联调受阻时实现仍可推进 |
| 3 | `references/worktrees.md`、`templates/runtime/sessions.mjs` 中现有起点解析 | 支持独立任务与依赖任务分别核对起始提交和合回目标。用临时双仓验证两项同仓任务隔离、跨端各自建树、连续阶段复用及初始化钩子只执行一次 |
| 4 | `references/review.md`、`references/acceptance.md`、`templates/spec/delivery.md` | 记录每个任务对应的试合并版本、双端组合、逐例结果与收尾授权。在临时仓演练同事提交导致的文本冲突、无文本冲突的行为回归、验证后目标前移，以及下游仍占用工作树时延后清理 |
| 5 | 安装器所分发的指南与模板、`tests/toolkit.test.mjs`、`tests/orca.test.mjs` | 运行受影响的测试及 skill 校验，演练旧项目升级和重复安装。兼顾项目自有模板与本地约定。验证后预览并更新 PEIS 父目录，使用 Orca 安装器同步角色，再用 `doctor` 和二次预览核对配置及待处理项 |

表内 `references/` 指 `templates/matt-full-stack/references/`。安装检查证明文件与配置就绪。对实际 bot 接单、Orca 初始化钩子以及业务联调，分别记录现场演练或尚未验证的范围。

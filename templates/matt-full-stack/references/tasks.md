# 需求范围与批准批次

先写出用户最终能观察到的业务结果，然后选工作方式，在规格评审里用一句话解释理由。

| 条件 | 如何安排 | 预约示例 |
|---|---|---|
| 一个结果，路径清楚，拆开没有交付或排期收益 | 一个任务。直接在公共和分端规格关联场景 | 改期后重新打开仍显示新日期 |
| 多个可分别验证的结果，分批交付、选择优先级或并行开工有实际收益 | 按业务结果给稳定 ID，各自说明负责人、场景和交付证据 | 前台改期、主管查改期记录可分别交付 |
| 一个结果，存在关键未知、必须先做的工作、兼容性风险或高代价回滚 | 一个业务任务，可分实现阶段。每阶段写清问题、继续所需的证据及交接产物，最后整体验收 | 团体改期先验证中途失败可整批回滚，再接名单和页面 |

权衡共享状态的一致性、并行协调成本和返工代价。文件数、用例数、文档长度和跨端本身都不能说明拆分有收益。业务规则由 Matt 集中澄清，技术未知可用最小实验取证；必须接通全链路才能判断时，优先走通最小真实链路。

单项沿用原规格。有独立子任务或有意义的阶段，才按 `spec/_templates/tasks.md` 写需求的 `tasks.md`。子任务内仍可有阶段。负责人是责任端或具体执行者，接口和共同业务约束统一引用 `shared.md`。本端收到的任务正文只摘录获批且相关的行。

评审同一修订的规格、拆分和启用的验收用例。把用户选择的全部或部分 ID 及确认来源记入 `shared.md`。开发依赖指缺少它就无法正确开工的契约、版本或阶段证据；联调依赖指最后组合验证所需的版本、服务或数据。前者缺失时说明缺哪项及可选批次，后者只推迟相应验收。每次收到回执，按[派单记录](claims.md)核实证据后重算可开工项，并在原会话回报。

可以按新证据调整已批范围内的顺序和阶段。业务行为、公共接口或获批范围改变时，暂停受影响任务，标出待重审的修订及依赖，让其余独立工作继续。这些做法借鉴 `to-spec`、`to-tickets` 与 `implement-spec`；只有用户显式调用时才进入上游原版 skill。

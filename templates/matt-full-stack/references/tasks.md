# 需求范围与批准批次

先写出用户最终能观察到的业务结果，然后选工作方式，在规格评审里用一句话解释理由。

| 条件 | 如何安排 | 预约示例 |
|---|---|---|
| 一个结果，路径清楚，拆开没有交付或排期收益 | 一个任务。直接在公共和分端规格关联场景 | 改期后重新打开仍显示新日期 |
| 多个可分别验证的结果，分批交付、选择优先级或并行开工有实际收益 | 按业务结果给稳定 ID，各自说明负责人、场景和交付证据 | 前台改期、主管查改期记录可分别交付 |
| 一个结果，存在关键未知、必须先做的工作、兼容性风险或高代价回滚 | 一个业务任务，可分实现阶段。每阶段写清问题、继续所需的证据及交接产物，最后整体验收 | 团体改期先验证中途失败可整批回滚，再接名单和页面 |

权衡共享状态的一致性、并行协调成本和返工代价。文件数、用例数、文档长度和跨端本身都不能说明拆分有收益。业务规则由 Matt 集中澄清，技术未知可用最小实验取证；必须接通全链路才能判断时，优先走通最小真实链路。

需求文档从草案起写在 `spec/<需求>/`。单项直接使用根目录，拆分为独立业务任务时按稳定编号建 `task1/`、`task2/` 等任务包，可附业务简称。需求根目录的 `shared.md` 维护共用规则和批准范围，`tasks.md` 由 Matt 维护任务入口、依赖与进展。`.matt/private/` 仅存运行状态、回执及本机配置。

每包从 `task.md` 进入，链接需求根目录的共用规则、适用的上游产物和本包 `acceptance.md`。涉及接口时 Backend 在前端对接前提供 `api.md`，每个接口只列方法与相对路径、业务入参和业务出参及说明。跨任务引用原定义。分端工作复杂时附 `frontend.md` 或 `backend.md`；交付结果写同包 `delivery.md`。旧需求继续按已批准文档的实际路径定位，后续产生的需求文档写到对应 spec。

每条依赖指定上游任务、所需产物和使用阶段。接口初版就绪可以开始前端模拟开发，真实服务可用才联调，业务验收按所需版本组合安排。只把必须等待上游完整交付的依赖登记为 `--needs`。以阶段产物为条件时，Matt 核对实际产物版本，并在任务总表登记。条件互不阻塞的任务可并行，各阶段解锁时按[派单记录](claims.md)认领。

业务预期及已批范围的变更由架构师定位受影响的任务、接口和用例，由 Matt 集中请用户确认。技术字段或路径调整由相关端更新同一份接口文件、通知使用方并调整对应测试。独立任务继续。

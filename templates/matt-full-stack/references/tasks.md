# 需求范围与批准批次

先写出用户最终能观察到的业务结果，然后选工作方式，在规格评审里用一句话解释理由。

| 条件 | 如何安排 | 预约示例 |
|---|---|---|
| 一个结果，路径清楚，拆开没有交付或排期收益 | 一个任务。直接在公共和分端规格关联场景 | 改期后重新打开仍显示新日期 |
| 多个可分别验证的结果，分批交付、选择优先级或并行开工有实际收益 | 按业务结果给稳定 ID，各自说明负责人、场景和交付证据 | 前台改期、主管查改期记录可分别交付 |
| 一个结果，存在关键未知、必须先做的工作、兼容性风险或高代价回滚 | 一个业务任务，可分实现阶段。每阶段写清问题、继续所需的证据及交接产物，最后整体验收 | 团体改期先验证中途失败可整批回滚，再接名单和页面 |

权衡共享状态的一致性、并行协调成本和返工代价。文件数、用例数、文档长度和跨端本身都不能说明拆分有收益。业务规则由 Matt 集中澄清，技术未知可用最小实验取证；必须接通全链路才能判断时，优先走通最小真实链路。

需求文档从草案起写在 `spec/<需求>/`。单项直接使用根目录，拆分为独立业务任务时按稳定编号建 `task1/`、`task2/` 等任务包，可附业务简称。需求根目录的 `shared.md` 维护问题、目标、用户场景、共用规则、来源记录、范围和批准结果，`tasks.md` 由 Matt 维护任务入口、依赖与进展。`.matt/private/` 仅存运行状态、回执及本机配置。

每包从 `task.md` 进入，链接需求根目录的共用规则、适用的上游产物和本包 `acceptance.md`。任务包必须能脱离原始需求包独立派单，业务规则、字段、接口和可观察预期写入仓库内的本版 spec。涉及接口时 Backend 在前端对接前提供 `api.md`，每个接口只列方法与相对路径、业务入参和业务出参及说明。跨任务引用仓库内的原定义。分端工作复杂时附 `frontend.md` 或 `backend.md`；交付结果写同包 `delivery.md`。已批准的旧需求按其现有记录路径读取，新增或修订的需求从草案起写到对应 spec。

每条依赖指定上游任务、所需产物、版本和使用阶段。接口初版就绪可以开始前端模拟开发，真实服务可用才联调，业务验收按所需版本组合安排。只把必须等待上游完整交付的依赖登记为 `--needs`。以阶段产物为条件时，Matt 核对实际产物版本，并在任务总表登记。条件互不阻塞的任务可并行，各阶段解锁时按[派单记录](claims.md)认领。

任务采用垂直切片。每个任务都要穿过本次结果所需的数据库、接口、页面和测试边界，并能单独演示或验收。一个任务包含关键未知、兼容性风险或高代价回滚时，可以先交付一个验证阶段；阶段必须写清继续所需的证据和交接产物。宽范围机械迁移按扩展、分批迁移、收缩排序，并把每一批登记成有明确阻塞边的任务。

派单前执行任务包自包含检查。只读本任务入口和仓库内链接，就能确定用户目标、规则、接口、验收预期、测试边界和完成条件。外部需求文档、个人磁盘路径或会话历史不作为 worker 的必需输入。

业务预期及已批范围的变更由架构师定位受影响的任务、接口和用例，由 Matt 集中请用户确认。技术字段或路径调整由相关端更新同一份接口文件、通知使用方并调整对应测试。独立任务继续。

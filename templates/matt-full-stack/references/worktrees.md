# 使用宿主工作树

`worktree: true` 是隔离要求，不是让 AI 建目录的授权。由当前开发工具的原生 worktree 功能创建并绑定到对应会话或 subagent；不在 shell 中执行 `git worktree add`，也不编写创建脚本或让子会话代建。`worktree: false` 复用指定 checkout，不走以下初始化和合回流程。

## 实现或修复：先固定来源，再创建

1. 父会话在派单时运行 `node .matt/runtime/sessions.mjs <frontend|backend> --worktree-base`。从 `worktreeBase` 登记**本端**原 checkout、当前本地分支、完整 SHA 和 dirty 状态。它们是创建依据，也是日后合回的目标；两端独立，不使用父仓、默认分支或远程同名分支。detached HEAD、无提交或映射有误就停下核对。未提交内容不会进入新树；若本单依赖它或无法分清，说明缺口，等待用户处理基线，不代为提交、stash 或复制。
2. 用宿主选择本端仓库，从记录的 SHA 建立新的**任务分支**和独立工作树，并绑定实现角色。宿主只能选择分支名时，仍以记录的 SHA 验证结果。在子会话实际目录核对仓库身份（原、新 checkout 的 `git rev-parse --path-format=absolute --git-common-dir` 应指向同一目录）、`git rev-parse --show-toplevel`、`git branch --show-current` 和 `git rev-parse HEAD`。根目录须是独立 checkout，任务分支非空且不同于原分支，HEAD 等于本端起始 SHA。宿主只支持父仓或 `main`、无法绑定或核对不符：该端标**待派单**，交回仓库、分支、SHA 和提示词；不改用共享目录、不在错误 checkout 开工。
3. 在已核对的新工作树里完成本端初始化后才开发。先看宿主创建钩子的运行结果：已成功完成的步骤直接复用，不重复安装。无钩子或有步骤未覆盖时，按本仓指令、README、包管理器和锁文件运行项目已有的 bootstrap 或依赖安装命令（例如 npm 锁文件用 `npm ci`，pnpm 锁文件用 `pnpm install --frozen-lockfile`）；没有依赖就记「无需初始化」。只在本端工作树执行，不复制原树的凭据。钩子失败、依赖缺失或命令不明确，记录步骤及原因并暂停，不换包管理器绕过、不把初始化失败当测试失败。

在 `delivery.md`（修复用原交接记录）按端登记原 checkout/分支/SHA、任务 checkout/分支、宿主绑定和初始化结果。续接已有任务工作树时核对先前记录，不以此刻原仓所在分支重定目标，也不重复初始化。

启用 E2E 时，从实际任务工作树启动服务或核实部署对应的构建版本；运行器回执里的原 checkout SHA 不能证明任务分支已经受验，不为验收提前合回。

## 只读审查：同样由宿主隔离，但不建合回任务

审查角色配置独立工作树时，只通过宿主绑定到[审查指南](review.md)指定的**待审 SHA**（提交审查）或**起始 SHA + 已核对补丁**（补丁审查）；核对仓库、实际目录和 SHA。不能绑定则标记审查阻塞。不在 reviewer 工作树安装开发依赖、改代码或发起合回。

## 父会话收尾：主动询问，不自动合并

本次所有相关端完成测试、两轴审查、修复复验及项目启用的 E2E 后，由父会话一次列出**有实现工作树的端**：`任务分支@已验证提交 → 创建时的本地原分支@当前提交`。对照起始 SHA 标明目标有无前移，说明还有无未提交改动，问「要把哪些端合回各自的原分支？」并等待。仅开发模式不等待未启用的 E2E；仍有失败或阻塞时只交付现状。未提交补丁不能直接合并：列出补丁摘要，询问是否先将已验证的本单改动形成提交，不擅自提交或丢弃补丁。

批准 spec 不是批准合回。仅处理用户明确选择的仓库与分支；动手前复核任务分支仍指向获审提交、没有遗留改动，目标分支、目标 checkout 状态和提交仍与询问时一致。目标已分叉、再次移动、checkout 有本地改动或遇冲突时，暂停说明差异，先确定整合与复验方案，不强制改写。无答复或选择暂缓就保留任务分支和工作树；同意本地合并也不包含推送或清理授权。

# E2E 用例与验收

从消费父目录运行 `node .matt/runtime/run.mjs plan` 读取 `enabled` 和 `provider`。关闭时只做本端测试与审查。启用时，在 Orca 团队由 Quality 负责用例和执行，其他宿主由父层验收会话负责。

## 开发前定用例

按本批的任务和场景 ID 对应用例。阶段证据记录在所属任务下，同一业务结果最后按完整用户路径验收；仅联调受阻时列出缺少的组合或服务，本端实现和其他独立项仍可继续。

1. 读公共 spec 草案，按场景 ID 设计具名用例。写明用例 ID、测试角色、前置状态与合成数据、操作、可观察的预期以及如何清理。按需求覆盖成功、拒绝或边界行为；涉及保存、权限或跨端同步时，写清从哪里重新读取以及应该看到什么。此时可以用业务动作描述步骤，执行时再定位控件。
2. 从共同父目录的 `.matt/runtime/docs.mjs` 读取 `specs`。Orca 用例写入 `<specs>/<需求名>/acceptance.md`。Midscene 用例直接复用或补充 `e2e/cases/*.yaml`，在需求目录登记“场景 ID → 用例 ID → YAML 路径及 case 名”，操作与断言只维护一份。
3. 把缺少预期的情形交给 Matt 澄清，在同一次 spec 评审中确认影响业务的决定。派实现前记录获批 spec 修订和对应的用例版本（提交或文件摘要）；实现端拿到同一版业务预期。修正定位或测试数据可以单独留痕；改变业务预期先修订 spec，再同步相关用例。保留原失败记录。

只验收已有版本时，优先复用相符的用例；缺少时先从已确认的行为补齐预期，再打开页面。修复任务用原症状及修复预期作依据。

## 执行固定版本

有试合并时，记录每端任务、目标与候选 SHA，从对应候选运行服务或核实部署标识。目标前移或冲突解决改变了版本对，要重跑受影响的 case 并保留原回执。验收结束后释放已登记占用的目录。

核对实际运行的前后端版本（部署标识或从任务工作树启动的记录）、测试地址与授权角色。按预定用例使用合成数据，完成相关持久化或跨端读回。每次验收运行选定的一个 provider。

- **orca**：按当前环境的 `orca-cli` skill 选择 CLI，加载 `skills get orca-cli --reference references/browser.md`。在本次任务的 Orca 工作区用 `tab create --url <测试入口> --json` 打开专用页，固定返回的 `browserPageId`。用 `snapshot --interactive` 找控件，用 `click`、`fill` 执行操作；按用例用 `wait`、普通 `snapshot` 或 `reload` 后重新读取文本核对预期。页面操作都带 `--page <browserPageId>`。保留必要的脱敏观察值或截图，清理测试数据并关闭本次创建的页。仅使用已授权的测试会话。
- **midscene**：按父目录 `.matt/AI_SETUP.md` 的 Midscene 步骤准备环境。从父目录运行 `node .matt/runtime/run.mjs test e2e/cases/<文件>.yaml`；读取本次生成的 receipt 和原生报告，逐个核对具名 case 和断言。

旧交接模板中的 YAML 栏可填写 Orca 用例文件及用例 ID。在本单 `delivery.md`（单独验收沿用其交付位置）登记 spec/用例修订、执行工具、实际版本对。逐个列出“用例 ID | 预期 | 实际观察 | 通过 / 失败 / 未验证 | 私有证据位置”；原始证据放父目录 `.matt/reports/<本次运行>/`，仅共享脱敏摘要。记录数据清理结果。已在真实环境观察到违反预期的标为失败；工具、服务或账号不可用、仅验证了 mock、或缺少读回证据时，相关用例标为未验证并说明原因。使用其他工具辅助排查时单列观察，保留原工具的结果。

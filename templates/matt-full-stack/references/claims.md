# 认领、派发和回执

两个入口都在消费父目录运行 `node .matt/runtime/tasks.mjs list`。登记保存在本机 `.matt/private/tasks.json`，记录任务引用、批准来源、执行者、返回会话、实际工作树及回执。共享规格和交付文档引用证据，私有记录保留运行细节。

按需求、完整工单、原症状、场景和仓库查找原记录。两个入口使用同一键，如 `frontend/reschedule/T01`。单项可用 `frontend/reschedule`；无工单的修复用双方可辨认的模块和原症状命名，无需建单。先核对同义描述，遇到疑似同一修复时先与已有执行者核实。重复来单沿用原键，`follow <键> --return-to <新会话>` 追加返回地址。用户只询问时直接从记录及实际版本答复。

下列子命令均接在 `node .matt/runtime/tasks.mjs` 后。会话用宿主的稳定标识，`--at` 填最近读取的该任务 `version`。发生版本竞争时重新读取状态；仅成功取得认领及开工回执的会话执行对应动作。

1. **登记批准。** `approve <键> --basis "<获批修订、场景和用户确认引用>" --return-to <原会话>`。只登记本批获批的端和任务。局部修复的 basis 可以是原症状、预期和用户明确修复的消息引用。重复 `--needs <责任端/任务键>` 表示开工需要相应交付，重复 `--integration <责任端/任务键>` 表示组合验收才需要它。可引用尚未登记的任务；确认批次缺少硬依赖时报告给用户。契约、阶段证据和测试环境等非派单条件由派发者核实并记录。
2. **认领后派发。** 核对 `list [<键>]` 的批准来源与证据。派发者执行 `claim <键> --actor <派发会话> --at <版本>`；成功后才发送一次，附键、返回地址和结果中的 `claimId`。成功送达后用 `sent <键> --actor <派发会话> --claim-id <本次标识> --at <版本> --evidence <消息回执>` 标为已派发。结果不明时用 `receipt <键> --actor <派发会话> --claim-id <本次标识> --at <版本> --evidence "<消息 ID 或发送结果不明>"` 登记结果。遇到超时、发送后进程退出或只有认领记录时，先对照原消息和 Orca 状态；确认未送达才可重新安排。直收且亲自执行的任务可在同一会话认领、开工。
3. **接单再建树。** 接单方核对本次标识、依据和真实执行上下文，使用 worker 时先执行 `accept <键> --actor <接单会话> --claim-id <随单标识> --at <版本>` 占用本单，按工作树指南创建或续接。看见 worker 实际启动后，以同一 actor、claimId 和最新版本执行 `start`，附 `--evidence <实际启动回执>`。直接在接单会话实现时，在实际开工时从已认领或已派发状态直接 start。由该接单会话管理唯一写入 worker，把实际 worker ID、checkout、分支、起点、目标及初始化回执记入交接记录。用 `progress <键> --actor <接单会话> --at <版本> --tree <宿主工作树标识> --evidence "<记录位置或阶段结果>"` 登记，后续阶段沿用原执行者及原树。共享 checkout 时串行；有未隔离的修改须先完成安全交接。
4. **交付与解锁。** `deliver <键> --actor <接单会话> --at <版本> --evidence "<固定提交或完整补丁、场景、测试及交接引用>"` 表示本端交付可供下游使用。Matt 按 `list` 的 `developmentBlockedBy` 和 `integrationBlockedBy` 分别安排开工和验收。派单记录固定本次使用的前置交付版本。前序返修换版后，用原键暂停、核对并重新安排受影响的下游，更新其证据；代码依赖还须核实同仓实际提交。将进展和最终结果回到 `returns` 中的会话；向用户区分实现交付、等待联调、通过验收和实际合回。
5. **暂停与返修。** `hold <键> --at <版本> --evidence "<阻塞、返修或待确认的差异>"`，同时通知执行者停止受影响工作，核对依赖方。按原授权返修或取得新批准后，用原键和最新 `--at` 再执行 `approve`，重列当前依赖，续接原执行者及原树。旧派单标识失效。若原会话确实无法续接，确认原 worker 停止后在 held 状态执行 `transfer <键> --at <版本> --actor <接替会话> --evidence "<停写及交接证据>"`。已合回且已清理后的新缺陷，引用旧交付登记新的修复。

6. **取消。** Matt 核对每个已批准的责任端任务，包括已派发、已开工、暂停及未启动的项。先停止相应 worker 并核对回执，再逐项执行 `cancel <键> --at <最新版本> --evidence <退出或未启动的依据、待执行操作的实际状态>`。迟到的回执只作记录。按实际结果更新 tasks.md、任务包的 delivery.md 及主事项，再向原会话汇报。

写入使用短时互斥锁和原子替换。若持续提示锁占用，核实 `.matt/private/tasks.lock` 中的本机 PID 和进程；只在确认写入进程已经退出后解除残留锁。读取原记录再恢复，避免重发或重建工作树。

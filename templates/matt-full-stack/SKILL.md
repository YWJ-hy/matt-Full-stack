## 先确定交付物

日常入口是 `$matt-full-stack` 加需求描述。使用 Matt 工程 skill 前，读取共同父目录 `CLAUDE.md`（没有则读 `AGENTS.md`）的 `## Agent skills` 段及其共享约定。若缺少约定，请用户在父目录环境会话按 `.matt/AI_SETUP.md` 第 1 节完成原版 setup，不在子仓初始化。其他环境缺项或升级也交由环境会话处理，就绪后从阻塞步骤继续。

优先采用用户点名的方法。自动流程只调用宿主允许模型调用的技能。若这类入口不可用，可读取工具包 `vendor/mattpocock/<短名>/SKILL.md` 及引用，注明是按随包参考执行；两者都不可用则报告缺项，停在该步骤。

> 手动入口：若用户要运行原版 `$mattpocock-skills:grill-with-docs` 或 `$mattpocock-skills:implement`，请用户分别在父会话或本端会话亲自发送该命令，待交付后再继续。其他仅限用户触发的技能同理；子会话提示词或读取副本不算启动原版。

请求带工单或项目要求跟踪时，父会话先按[工单交接](references/issues.md)确认来源，再把同一完整引用带入本次交付。没有引用且项目未要求工单，直接用本地 spec 或故障预期，不为派单建工单。

- **已有行为异常**：用户直接报告故障、要求只排查或排查并修复，走下方「排障」，不先写功能 spec 或猜责任端。
- **新功能或行为变更**：进入「功能交付流程」，复用已有决定；用户指定的方法随单传给实现会话。
- **只验收已有版本**：`e2e.enabled: true` 时直接执行下方「验收实际组合」，交付结果即停；只有用户也要求修复才将失败转入排障。关闭时说明未启用，不自行切换模式。
- **独立交付物**：调研结论用 `$mattpocock-skills:research`，一次性原型用 `$mattpocock-skills:prototype`，审查改动按[审查分流](references/review.md)先确定仓库和比较基线，再选提交或补丁，PR 正文用 `$mattpocock-skills:pr`。交付即停；审查不是修复授权。需要委派时传该任务自己的范围与交付物，不套实现单。

在共同父目录执行 `node .matt/runtime/run.mjs plan` 读取项目的 E2E 开关和执行工具。配置错误先修复；启用时按[用例与验收](references/acceptance.md)准备、执行和留证。

**工作树的创建与收尾（功能和修复）。** 角色启用 `worktree` 时按[工作树指南](references/worktrees.md)由宿主从本端当前分支创建并绑定，先核实工作目录和初始化结果再开发。整单完成所需验证后，父会话须列出每端任务分支和创建时的原分支，单独询问是否合回；未获确认保留现场。

## 排障：先复现，再决定是否派修

1. **复现和定位。** 调用 `$mattpocock-skills:diagnosing-bugs`，限定本阶段为诊断。记录原操作、预期和实际；在授权环境用最小能显示同一症状的检查跑出失败，按证据定位。已有可信复现和根因可复用。无复现就列已尝试的检查，索取脱敏日志、数据或可复现环境；根因未证实不猜端派修。关闭 E2E 仍可用本端测试、HTTP 等检查，不自行开启 E2E。
2. **以用户授权划界。** 只排查或仅报告异常：交付复现方法、证据、已证实的根因或仍未知之处，到此为止，不改产品代码。要求修复且已定位：按[派单模板](references/dispatch.md)将故障预期、失败证据、本端测试边界及起始 SHA 派给责任端；优先复用原会话，没有则新开。两端均有偏差分别派，夹具、登录或用例问题留在父层按授权处理。
3. **复验原症状。** 在修复版本上重跑最初的复现，并核对本端回归测试和审查。启用 E2E 时再对实际版本组合重跑相关 case；关闭时注明未执行 E2E。原复现未跑、仍失败或仅替身通过，如实列为未验证或仍失败，不宣称已修好。

## 功能交付流程

1. **先访谈，再定方案。** 父会话直接使用 `$mattpocock-skills:grilling` 和 `$mattpocock-skills:domain-modeling`。先读需求、相关代码与领域约定；用具体场景找出仍需用户决定的行为。把本轮能决定的问题编号列出，逐项给建议，等答复再问依赖这些答案的问题。可查的事实自己查，已决定的不重问；没有未决问题就直接起草。术语确定时更新项目级术语表，有重要且难逆的取舍才记录 ADR。
2. **起草同一修订的规格。** 参照 `spec/_templates/`，在 `spec/<需求名>/` 建 `shared.md` 和**需要改动的端**的 `frontend.md` 或 `backend.md`（两端都改就都建）。公共 spec 是业务行为、接口和验收场景的唯一依据；分端 spec 按场景 ID 说明本端范围和公开测试边界。另一端必须知道的约束移到公共 spec，不互相引用实现细节。
   启用 E2E 时，派实现前由 Quality（其他宿主由父层验收会话）按[用例与验收](references/acceptance.md)从草案独立设计具名用例，复用已有 case。根据用例发现的歧义补齐 spec。
3. **请用户评审，到此等待。** 给出本版公共及各端 spec 的链接和修订号，用业务语言列出关键假设、成功/失败预期与两端各交付什么，问「按这版开发吗？」即使需求没有疑问，也不把最初的“请实现”或对访谈问题的回答当作批准。启用 E2E 时附用例引用，用户只需确认业务预期。收到修改意见先同步规格和受影响的用例、标新修订并再次请审；用户明确同意这版才登记批准。在此之前不派实现、不改产品代码；已有明确批准且内容未变的同一版无需重问。
4. **按批准版派单。** 按[派单模板](references/dispatch.md)给责任端公共 spec 和本端 spec、场景 ID、测试边界及本端起始 SHA。登记会话引用；无法启动时交付待派提示词。实现或验收中若要改变用户可见行为、接口或已批范围，暂停受影响工作，回到评审；获批后再同步相关端及受影响的验收用例。
5. **独立交接。** 父会话按 `spec/_templates/delivery.md` 在需求目录的 `delivery.md` 逐端登记实际版本或补丁、测试、审查及未验证项；测试失败或审查未完成则报告阻塞。仅开发模式按场景做本端测试，不编写 E2E 用例，交接后报告「开发完成；按项目配置未执行 E2E」，不宣称联调通过。
6. **验收实际组合。** 启用 E2E 时，按[用例与验收](references/acceptance.md)用选定的工具逐条执行开发前定好的用例，交付版本对、实际观察、逐例结论和证据。失败且已获修复授权时，带版本对、失败 case 和脱敏证据转入「排障」。
